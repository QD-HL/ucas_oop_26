| 项 | 内容 |
|---|---|
| 仓库 | `https://github.com/ISCAS-SSG/Ripple`（Ripple 消息引擎，中科院软件所） |

Ripple 是一个**分布式配置同步与消息推送引擎**：多个服务器节点组成集群，客户端向任一节点写入配置后，
节点之间按某种「拓扑（overlay）」把变更同步给其余节点，再推送给订阅了该配置的客户端。

## 三、运行时结构

### 3.1 进程与端口

每个进程开**两个端口**：

- **Netty TCP（`apiPort`）**：节点间同步、客户端与服务器通信，走自定义二进制帧协议；
- **Jetty HTTP（`uiPort`）**：Web 控制台。

### 3.2 启动参数（本实验实际使用的形式）

| 参数 | 含义 |
|---|---|
| `-Did` | 节点 id（1/2/3） |
| `-Daddress` / `-DapiPort` / `-DuiPort` | 监听地址与两个端口 |
| `-DstorageLocation` | SQLite 数据库文件位置 |
| `-Dprotocol` | 同步拓扑：`star` / `tree` / `hashing` / `expander` / `gossip` |
| `-Dnodes` | 静态集群成员表，如 `1:127.0.0.1:3001,2:...,3:...` |
| `-DnodeSelector` | 客户端选点策略：`hashing` / `load-balanced` |

**没有服务发现**：集群成员完全由 `-Dnodes` 静态给定。这一点对实验很关键——单机上起三个进程即可复现一个集群。

### 3.3 存储

`Storage` 是一组接口（`ItemService` / `MessageService` / `AckService` + `RecycleStrategy`），
有目录实现、持久化内存实现、SQLite 实现三套；本实验用 SQLite（`-Xmx256m` 即可跑三节点）。

## 四、核心对象与职责

| 对象 | 职责 | 与第一/二阶段改动的关系 |
|---|---|---|
| `Node` | 总装：收到报文后分发、落库、通知订阅者、同步对等节点 | 调用链上端 |
| `Tracker` | 记录每条消息的 ACK 进度，`Worker` 每 10 秒触发重试 | 间接 |
| `Overlay` 家族 | 决定「这条变更要同步给哪些节点」 | 决定实验中同步报文条数 |
| `AbstractMessage` 家族 | 24 种报文共同基类，持有 `uuid`、`type`、`applicationName`、`key`、`lastUpdate` 等 | **uuid 与元数据字段就是带宽浪费的来源** |
| `Encoder` / `Decoder`（24 对） | 每种报文一对编解码器，全部通过 `TypeHelper` 读写字段 | 24 对自动继承 UUID 与 VarInt 字符串优化；8 对在第二阶段改为枚举 Tag / SVarInt / Timestamp |
| `TypeHelper` | 线格式原语：uuid、string、varint/svarint、timestamp、enum tag、boolean 的读写 | **第一阶段唯一改动对象；第二阶段扩展变长与枚举原语** |
| `CompactFrameEncoder` / `Decoder` | 帧级边界切分与自适应压缩：1~5 字节 `VarInt((len << 1) \| flag)` 帧头 | **第二阶段新增，替换固定 4 字节 LengthField 帧处理器** |
| `FrameCompressor` / `DeflateFrameCompressor` | 帧压缩策略接口与 JDK Deflate 单例实现（含 `maxLength` 防炸弹保护） | **第二阶段新增（策略模式），对 >=256B 大帧自适应压缩** |
| `Storage` 家族 | 落盘与查询 | 不受影响（UUID 仍以文本存表） |
| `ClientDispatcher` | 决定「推送哪些订阅客户端」；`DefaultClientDispatcher` 实际复用 `SYNC_REQUEST` | 影响统计口径 |
| `NodeSelector` | 客户端选点策略 | 与改动无关 |

## 五、帧协议与一次 PUT 的完整链路

### 5.1 帧协议

服务端与客户端都在 Netty pipeline 里装了：

```java
pipeline.addLast(new LengthFieldBasedFrameDecoder(1024 * 1024, 0, 4, 0, 4));
pipeline.addLast(new LengthFieldPrepender(4));
```

即每个 TCP 载荷是：**4 字节大端长度前缀 + 1 字节报文类型 + 报文体**。

### 5.2 一次 PUT 的链路

1. 客户端 `Api.putAsync` 把 `PUT_REQUEST` 发给某个服务器（节点由 `NodeSelector` 选）；
2. 该服务器 `Node.propagateMessage`：查重（`MessageService.exist`）→ 落库 → `Tracker.initProgress()`；
3. **两条支路**：
   - `doNotifyClients()`：向订阅了该 `(app,key)` 的客户端推 `SYNC_REQUEST`；
   - `doSyncWithServer()`：按 `Overlay.calculateNodesToSync()` 得到对等节点，逐个发 `SYNC_REQUEST`，并 `Tracker.recordAck()`；
4. 对端 `SyncRequestHandler` 落库并回 `SYNC_RESPONSE`；
5. 每 10 秒 `Worker` 让 `Tracker` 重试未确认的消息。

**关键观察**：`SYNC_REQUEST`、`PUT_REQUEST`、`DISPATCH_REQUEST` 这些「运数据」的报文都属于
`AbstractMessage` 家族，身份字段（uuid）和内容字段（app/key/value）混在同一字节流里，
编码完全由 `TypeHelper` 决定——这是本次优化的入口。

### 5.3 字段编码规则（改动前）

| 字段类型 | 线格式 | 字节数 |
|---|---|---|
| `String` | 4 字节长度 + UTF-8 内容 | 4 + n |
| `UUID` | **4 字节长度 + 36 字符 ASCII** | **40** |
| `int` | 4 字节大端 | 4 |
| `long` / `double` | 8 字节 | 8 |
| `byte` / `boolean` | 1 字节 | 1 |

UUID 本质是 128 位（16 字节），却被写成 36 个字符的文本再加 4 字节长度 = 40 字节，
**每个 UUID 固定浪费 24 字节**。

## 六、改动的对象分析

改之前先确认影响面，结论是这条链路只收口在一个对象上：

| 事实 | 数据 |
|---|---|
| `TypeHelper.writeUuid` / `readUuid` 的调用点 | **64 处**（32 处写 + 32 处读） |
| 分布文件 | **48 个**：`ripple-common/tcp/{encoder,decoder}` 44 个 + `ripple-server/tcp/{encoder,decoder}` 4 个 |
| 存储层 / HTTP 层 / JSON 序列化是否调用 | **否**（全仓 grep 无命中） |

因此改动只影响**线格式**这一层：SQLite 落盘格式不变（UUID 仍以 36 字符文本存表）、
Web 控制台输出不变、客户端列表签名（SHA-1 hex）不变。

从对象设计的角度说：`encoder` 依赖的是「把一个 UUID 写进 `ByteBuf`」这个**契约**，
`decoder` 依赖「从 `ByteBuf` 读回一个 UUID」；**契约不变、实现变化，调用方零改动**。
这正是 `TypeHelper` 这层封装的价值。

## 七、具体的代码改动

### 7.1 唯一修改的文件

`ripple-common/src/main/java/ripple/common/helper/TypeHelper.java`（全文 62 行），
只改两个静态方法，**3 增 2 删**：

```diff
     public static UUID readUuid(ByteBuf byteBuf) {
-        return UUID.fromString(TypeHelper.readString(byteBuf));
+        return new UUID(byteBuf.readLong(), byteBuf.readLong());
     }

     public static void writeUuid(UUID value, ByteBuf byteBuf) {
-        TypeHelper.writeString(value.toString(), byteBuf);
+        byteBuf.writeLong(value.getMostSignificantBits());
+        byteBuf.writeLong(value.getLeastSignificantBits());
     }
```

### 7.2 改动后的两个方法（完整）

```java
public static UUID readUuid(ByteBuf byteBuf) {
    return new UUID(byteBuf.readLong(), byteBuf.readLong());
}

public static void writeUuid(UUID value, ByteBuf byteBuf) {
    byteBuf.writeLong(value.getMostSignificantBits());
    byteBuf.writeLong(value.getLeastSignificantBits());
}
```

要点：

- `UUID.getMostSignificantBits()` / `getLeastSignificantBits()` 与 `new UUID(long, long)`
  是严格互逆的两个 API，**写入顺序（hi 在前）必须与读取顺序一致**；
- `writeUuid(null)` 的异常类型没变：旧实现由 `writeString` 显式抛 `NullPointerException("value")`，
  新实现由 `value.getMostSignificantBits()` 解引用时抛 `NullPointerException`——类型一致、消息不同，
  且仓库内没有调用点会传 `null`；
- 其余方法（`readString` / `writeString` / `readBoolean` / `writeBoolean`）**一行未动**。

### 7.4 第二阶段（第二版）全链路紧凑编码与自适应帧压缩扩展

在第一版 UUID 二进制化的基础上，第二阶段针对「短包元数据仍有冗余」与「大 JSON 负载下收益衰减至个位数」两个问题，完成了以下架构与代码演进：

1. **`TypeHelper` 原语扩展（`ripple-common/.../helper/TypeHelper.java`）**：
   - **变长字符串长度前缀**：`writeString` / `readString` 的长度前缀从 4 字节 `int` 改为 `VarInt`（`<= 127` 字节的短字符串长度前缀仅占 1 字节，全仓 24 对编解码器自动生效）；
   - **单字节操作类型枚举 Tag**：新增 `writeOperationType` / `readOperationType`（映射 `update` / `delete` / `incremental_update` 为 `0x00`~`0x02`）与 `writeAtomicOperation` / `readAtomicOperation`（映射 `add_entry` / `remove_entry` 为 `0x00`~`0x01`），未知字符串以 `0xFF` 标签安全回退；
   - **变长整数与紧凑时间戳**：新增无符号 `writeVarInt` / `readVarInt`、ZigZag 带符号 `writeSVarInt` / `readSVarInt`、`writeVarLong` / `readVarLong`、`writeSVarLong` / `readSVarLong` 以及 `writeTimestamp` / `readTimestamp`（现代毫秒时间戳占 6 字节）。
2. **8 对具体报文编解码器对称升级**：
   - `SyncRequestEncoder/Decoder`、`DispatchRequestEncoder/Decoder`、`GetResponseEncoder/Decoder`、`IncrementalUpdateRequestEncoder/Decoder`：操作类型改用 1 字节枚举，时间戳改用 6 字节 `Timestamp`，节点 ID 改用 `SVarInt`（常见节点编号 1/2/3 仅占 1 字节）；
   - `SubscribeRequestEncoder/Decoder`、`UnsubscribeRequestEncoder/Decoder`、`GetClientListResponseEncoder/Decoder`：端口号与列表项数改用 `VarInt`；
   - `AckRequestEncoder/Decoder`（`ripple-server`）：`sourceId` 与 `nodeId` 改用 `SVarInt`。
3. **帧协议重构与策略模式自适应压缩（`ripple-common/.../tcp/`）**：
   - 新增策略接口 `FrameCompressor` 与默认 JDK Deflate 实现 `DeflateFrameCompressor`（单例 `INSTANCE`，含 `maxLength` 防压缩炸弹上限保护）；
   - 新增 `CompactFrameEncoder` 与 `CompactFrameDecoder`，在 `ServerChannelInitializer` 与 `ClientChannelInitializer` 中替换原本固定 4 字节的 `LengthFieldBasedFrameDecoder` / `LengthFieldPrepender`；
   - 帧头格式为 `VarInt((payloadLength << 1) | compressedFlag)`：`<= 63` 字节的短包帧头仅占 1 字节（省 3 字节）且跳过压缩；`>= 256` 字节的大帧自动调用 `FrameCompressor.compress`，仅当压缩后更小时才置 `compressedFlag = 1`，不可压缩的高熵数据自动回退为未压缩帧。

### 9.4 三个口径必须分开

- **单帧报文**：−36% ～ −58%（最能体现编码改动）；
- **TCP 载荷**：−40%（真正承载业务数据的字节）；
- **链路总字节**：−18%（含每包约 54 字节的 TCP/IP/以太头与纯 ACK，最保守）。

文中结论统一使用「**业务报文字节降低 42%**」这一口径。

### 9.5 收益边界与第二阶段全负载区间突破

第一阶段仅做 UUID 二进制化时，固定工作负载只改 value 大小：4 B 时 −42.2%，1 KiB 时 −5.9%，8 KiB 时 −0.8%。因为每条报文省下的字节数固定（每个 UUID 24 B），而报文随 value 线性增长。

第二阶段引入字段级紧凑编码（VarInt 字符串前缀 + 1B 操作枚举 + SVarInt 节点号 + 6B 时间戳）与 `CompactFrameEncoder`（1~2B VarInt 帧头 + 256B 阈值自适应 Deflate 压缩）后，含帧头 TCP 载荷实测对比如下：

## 十一、已知问题与限制

| 问题 | 说明 |
|---|---|
| 兼容性 | 新旧版本不能混跑：第二版采用 VarInt 紧凑帧头与紧凑字段编码，**整个集群（server + client）必须一起升级** |
| CRLF 污染 | 从 Windows 复制到 WSL 的副本会让 241 个文件显示「被修改」，`git diff` 全是行尾差异。务必用 `git clone` |
| 既有 NPE | `Tracker.retrySending` / `getPendingMessages` 在 10 秒周期里会抛 NPE（`Tracker.java:65/81`），**改动前后相同、与本改动无关**；压测时会产生重试噪声 |
| 测试环境 | 只在单机 loopback 上测过，未在真实弱网（限速/丢包/高 RTT）下验证 |
| 统计口径 | 客户端推送复用的是 `SYNC_REQUEST`（不是 `DISPATCH_REQUEST`），统计时需计入 |
